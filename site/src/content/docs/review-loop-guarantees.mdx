The [worker review loop](/review-loop/) gates merges on review verdicts, so its behaviour under crashes, retries and concurrent requests has to be stated exactly. This page does that for each operation. Each claim links to the test that proves it. Claims about concurrency are proven on PostgreSQL, which production uses, by forcing the race: a third connection holds the lock both requests need, both requests are seen waiting on it, and only then is the lock released.

## The model in one paragraph

No operation is "exactly once" in the network sense: a client can always lose the response. Each write is instead **at-least-once delivery with an exactly-once effect**. A retry with the same idempotency key returns the stored result and writes nothing new. A conflicting request with a different value for the same key is refused. Writes that race are put in order by one of three mechanisms: the **project lock** (a PostgreSQL advisory transaction lock per project, taken by start worker, finish worker run and record review round), a **guarded transition** (an `UPDATE … WHERE status IN (…)` that only counts when exactly one row changed), or a **unique index**. A worker's claim on a ticket is a **lease** with a number, `lease_epoch`, that goes up by one on every start. Starting work on a ticket another worker holds is how a lease is taken over, and the older holder is then fenced.

| Finish worker run (`finish_worker_run`) | Exactly-once effect | (run id, `head_sha`) | Project lock; guarded `queued`/`running` → finished; refused once the lease was taken over | [^finish-replay] [^finish-pg] [^takeover] |
| Record review round (`record_review_round`) | Exactly-once effect | (ticket, stage, round number, workflow step) | Project lock; unique index `uq_agent_run_review_round` | [^round-replay] [^round-pg] [^round-index] |

## Start worker

`POST /api/v1/projects/{id}/agent-runs/start-worker` takes the ticket's lease and opens an implementer run.

- **Semantics.** A fresh start bumps `lease_epoch` by exactly one and returns it [^epoch]. While the run is open, a repeat by the **same credential** for the same workflow step returns the same run with `idempotent: true` and does not bump the epoch [^start-retry]. This holds when the retry races the first attempt: both requests get the same run id and epoch, and only one run is opened [^start-pg].
- **Fencing.** The decision between "this is a retry" and "this is a takeover" is made under the project lock, from the ticket as it is after the lock is taken.
- **On timeout.** Retry with the same credential and body. You get either the run the first attempt opened or a new one if it never committed; either way there is one open run for your lease.
- **Refusals.** A parked item gets `409 loop_needs_human`, and a start that finds the budget already spent parks the item in the same call [^round-cap] [^budget-usage].

### Worker A crashes after start: who can take over, and when

There is **no lease timeout**. Any project editor (or a service key with the loop scopes) can call start worker on the in-progress ticket at any time; the call takes the lease immediately and bumps the epoch [^takeover]. SessionFS does not detect that A died: a person or an orchestrator decides that A is gone. A stays recorded as an implementer of the ticket, so A can never be the independent reviewer of B's work [^takeover-identity].

If two workers start at once, both succeed one after the other: the later start holds the lease and the earlier one is fenced [^takeover-pg].

### A finishes after B took over: is A fenced?

Yes. Each start-worker run records the run it continues. Once B's run continues A's, A's finish is refused with `409 lease_superseded` and A's run records no head commit [^takeover] [^takeover-pg]. So a late finish from A can never change which commit the ticket is at: loop status, workflow gates and approval gates keep using B's commit [^late-finish]. A's spend is not lost: A can still report its tokens on the run's usage endpoint, and the budget counts them [^takeover-usage].

## Finish worker run

`POST /api/v1/projects/{id}/agent-runs/{run_id}/finish` closes the run with its head commit, exit reason and usage.

- **Semantics.** Idempotent on (run id, `head_sha`). Repeating a finish with the same head returns the stored result (`idempotent: true`) and does not add usage again; a finish with a different head after the run finished gets `409 head_sha_conflict` [^finish-replay] [^finish-conflict]. Two identical finishes racing add usage once [^finish-pg]; two with different heads racing leave exactly one head and refuse the other [^finish-conflict-pg].
- **Who can finish.** The credential that started the run, a key rotated from it, or a project admin. Anyone else gets `403 worker_run_not_yours` [^finish-owner] [^rotate-finish].
- **On timeout.** Retry with the same `head_sha`. Never retry with a different head: if the first attempt landed, the retry is refused.

## Record review round

`POST /api/v1/projects/{id}/loops/{loop_id}/rounds` records the reviewer run, posts the verdict and may close or park the item.

- **Semantics.** The idempotency key is (ticket, stage, round number, workflow step). A retry from the same credential returns the stored round (`idempotent: true`), even if the retried body differs, and never posts a second verdict [^round-replay] [^round-idem]. Two identical rounds racing (one reviewer, two pods) record one round and one verdict [^round-pg]. A unique index backs this up when the read misses the race [^round-race] [^round-index].
- **Another reviewer, same number.** A different credential asking for a taken round number gets `409 review_round_taken`, including when both race [^round-taken] [^round-taken-pg]. Record the next number.
- **Trust.** Whether the verdict is trusted comes from the credential and the trusted-reviewer registry, never from the request body [^untrusted].
- **Refused rounds keep their spend.** A round refused after the review ran (the item is parked or closed) records its tokens on an errored run that takes no round number and posts no verdict [^refused-usage].
- **On timeout.** Retry with the same round number. If you get `review_round_taken`, someone else holds that number.

### A verdict arrives for an old head commit

A round is accepted for any full commit id. Readiness is always computed for one exact commit, so a clean verdict for an older commit never makes the current head ready, even when it arrives last [^old-sha] [^sha-moved]. A newer `CHANGES-REQUESTED` verdict for any commit makes the ticket not ready [^out-of-order].

**Closing an item does not check the commit.** A trusted clean round on an older commit can close the loop item while the worker has already pushed a newer one. The item stops being worked, but readiness at the newer commit stays false, so the merge gate still holds [^close-sha]. Review the newer commit before merging: it is not ready until a trusted clean verdict is bound to it. Reviewers should review the newest commit the worker reported.

## Close item

**Automatic close** happens in a review round when the verdict is a trusted strict `VERIFIED-CLEAN`, no finding is open, the review history is complete, and the reviewer is independent of every implementer. It fails closed: an unknown implementer, an unresolvable key minter or a truncated history never closes [^same-identity] [^unknown-impl] [^truncated] [^minter]. It is a guarded transition, so it happens at most once.

**A person's close** (`POST …/loops/{loop_id}/children/{ticket_id}/close`) settles a `needs_human` item as done. It is people-only, and a guarded `needs_human` → `done` transition: two closes racing give one `200` and one `409` with a single close record [^close-pg]; a retry of a close that already landed gets `409` [^close-retry]. **On timeout:** read the loop status; a `409` after a timeout usually means your close landed.

Neither close changes the ticket's own status [^close-ticket].

## Merge readiness

`check_merge_readiness` (`GET …/tickets/{ticket_id}/readiness?sha=`) is a pure read with no side effects: it raises no approval requests [^readiness-read]. It is ready only when the latest trusted verdict, in the order verdicts were recorded, is a strict `VERIFIED-CLEAN` bound to exactly the requested full commit, the reviewer is independent of every implementer, and no harmful finding is open [^sha-moved] [^short-sha] [^out-of-order]. A review history longer than the loaded window fails closed [^truncated-readiness].

## Merge check post

After a verdict, an approval decision, a policy change, a pull request webhook or an explicit trigger (`POST …/tickets/{ticket_id}/merge-check`), SessionFS recomputes readiness and posts the **SessionFS review loop** check run on GitHub (or a commit status on GitLab).

- **Semantics.** Best-effort and at-least-once. The post runs in a detached task after the triggering request commits. A GitHub call is tried up to three times on transport errors and `5xx`, and never retried on a `4xx` [^check-retry]. A task lost with its process is not retried later.
- **Keyed by commit.** Each commit gets its own check run, and a run for an older commit is never flipped green after the fact [^check-sha]. A check covering several tickets is green only when every linked ticket is ready at that commit [^check-all].
- **Ordered per commit.** Every evaluation of a commit takes the next number in a sequence for that commit just before it reads readiness, so a higher number always saw newer state. Just before sending, the post records its number with a guarded `UPDATE` that only succeeds when no newer evaluation has posted. An evaluation that read "ready" before a newer `CHANGES-REQUESTED` verdict is therefore skipped once the newer `action_required` was sent, and never turns the check green [^check-order]. A retry of the same evaluation still posts. If two posts are in flight at once and the older request reaches GitHub or GitLab last, its sender re-sends the newest recorded state afterwards, so the last request to land carries the newest result [^check-order-repair]. GitLab commit statuses follow the same rule [^check-order-gl]. No database lock is held while a GitHub or GitLab call is made. The readiness call is still the authoritative gate before a merge.
- **On failure.** Call the merge-check trigger route. It recomputes from the current state.

## Budget parking

Token, dollar and round limits are checked by start worker, finish worker run and record review round, all under the project lock, so each check sees what the others committed. When a finish and a round that each stay under the budget land at once, the second one sees the first one's spend and parks the item exactly once, with one notification [^budget-pg]. Parking is a guarded transition, so it happens once [^round-cap] [^budget-finish].

The plain usage endpoint (`report_agent_run_usage`) records spend but does not park. A limit passed that way is enforced by the next start, finish or round, which parks the item and refuses [^budget-usage]. So the spend of in-flight work can go past a limit; no new work starts after it.

## Approval raise

Approval requests are raised only on write paths (a verdict, a decision, a policy change, a webhook or the merge-check trigger), only for the commit the latest trusted clean verdict is bound to, and only when the ticket is otherwise ready. Readiness reads never raise one [^readiness-read]. The insert uses `ON CONFLICT DO NOTHING` on a unique index over pending requests, keyed by (policy, ticket, commit), so concurrent triggers converge on one request [^approval-pg]. An expired request frees the key, and concurrent triggers then raise exactly one fresh request [^approval-reraise]. Concurrent approvals settle quorum once, and one person voting twice at once records one decision [^approval-pg].

## Work queues

The `review_until_clean` and `implement_until_done` queues under the loop follow the same pattern:

- **Claim.** An item is claimed by a guarded `UPDATE`; two wakes racing for one item have one winner [^claim-pg]. An item whose directive is still open is never claimed again; the next wake re-emits the **same** directive instead [^reemit] [^crash-replay].
- **Settle.** `complete_work_queue_step` is idempotent on `directive_id`: a repeat returns the stored outcome without posting the verdict again [^settle-replay]. The item row is locked first, so two settles of one directive racing give one settle and one replay with a single verdict [^settle-pg]. A directive that is not the item's open one is refused with `409 directive_mismatch`, posting nothing [^settle-lease]. A settle that passes the ticket's `lease_epoch` is refused with `409 stale_lease_epoch` once the lease moved on, and the directive re-emits [^settle-epoch].
- **Backoff.** A failed directive backs off 2, 5, 15, then 60 minutes and the item fails after the queue's attempt limit [^backoff].

## A reviewer key rotated mid-loop

Reviewer trust is bound to the exact service key. After a rotation, the new key's verdicts are untrusted, and close nothing, until an org admin registers the new key as a trusted reviewer [^rotate-trust]. A worker whose key is rotated mid-run finishes the run with the new key [^rotate-finish].

Rotation never makes a reviewer independent. A key counts as everyone who minted or rotated it along its rotation chain: the person who rotated the implementer's key cannot close the item or make the ticket ready [^rotate-independence] [^rotate-chain]. A broken or cyclic chain fails closed [^broken-chain].

## What is not guaranteed

- **No ordering across tickets or projects.** Locks are per project and per row. Two loops in different projects run fully in parallel, and events on different tickets have no defined order.
- **No lease timeout or crash detection.** A crashed worker holds its lease until someone takes it over.
- **Background work is best-effort.** Merge check posts, checklist proposals from findings and notifications run after the request commits and are not retried if the process dies. Jira outbox rows are retried by their sweep.
- **Clocks.** Fencing a superseded worker uses the recorded run lineage, not time. Ordering of verdicts and runs uses timestamps written by the API servers, so it assumes their clocks agree to well under the time between two rounds. Approval request expiry and backoff use the server clock.
- **Only start worker takes over.** The plain ticket start (`start_ticket`) only starts an `open` (or, with force, `blocked`) ticket. If a running worker's ticket is moved out of `in_progress` and started again that way, the lease epoch moves on but the worker's finish is not refused: only a start worker run fences an earlier one.
- **SQLite.** Self-hosted development on SQLite has no row or advisory locks; SQLite runs one writer at a time, and the unique indexes and guarded transitions above still hold, but the concurrency results on this page are proven on PostgreSQL. Run production on PostgreSQL.
- **A person still merges.** A green check and a ready answer say the review gate passed for one commit. They do not run your tests or merge for you.
