title: "REST API"

The SessionFS API server exposes a REST API for session management, auditing, sync, and settings.

## Base URL

- **Cloud:** `https://api.sessionfs.dev`
- **Self-hosted:** Your deployment URL

## Authentication

All endpoints (except signup) require a Bearer token:

```
Authorization: Bearer sk_sfs_...
```

Two key kinds:

- **User keys** — created via `POST /api/v1/auth/keys`. Tied to a single user, inherit all of that user's permissions. Legacy keys are back-filled to `scopes=["*"]`.
- **Service keys (v0.10.10+)** — created via `POST /api/v1/orgs/{org_id}/service-keys`. Org-scoped, expirable, and restricted to an enumerated `scopes` list (e.g. `["handoffs:write", "agent_runs:write"]`). Deny-by-default: a service key only reaches a route handler that explicitly opted in via `require_scope(...)`. The recommended credential for cloud agents (Bedrock, Vertex), CI runners (GitHub Actions, GitLab MR), and integration partners.

Structured 401/403 error codes: `api_key_revoked`, `api_key_expired`, `service_key_not_allowed`, `insufficient_scope` (with `required` + `current` arrays), `cross_org_denied`, `service_key_project_required`, `service_key_project_not_registered`, `service_key_project_ambiguous`.

Org-scoped, scope-restricted API keys for cloud agents, CI runners, and integration partners. Org admin role + Team+ tier required for mutations. Raw key returned exactly once on create + rotate; the list endpoint only returns `key_prefix`.

| Method | Path | Auth | Description |
|--------|------|------|-------------|

| GET | `/api/v1/orgs/{org_id}/service-keys` | Bearer (org member) | List service keys for the org |

| `knowledge:read`, `knowledge:write` | ✅ live (v0.10.19; project context + wiki since v0.29.1) | Knowledge entries: `GET /entries`, `GET /entries/{id}`, `POST /entries/add`, `PUT /entries/{id}` (dismiss/update/refresh/promote/supersede). | `personas:read`, `personas:write` | ✅ live (v0.10.20) | Persona list/get + create/update/delete |

User keys also need editor standing; `cost_budget_usd` is org-admin only, and service keys never see or set dollars |
| `agent_feedback:read`, `agent_feedback:write` | ✅ live (v0.17) | `GET /agent-feedback`, `GET /agent-feedback/summary`, `POST /agent-feedback` |
| `marketplace:read`, `marketplace:write` | ✅ live (v0.16) | Marketplace search/inspect/download/feed + personal package/registry publishing |
| `skills:read`, `skills:request`, `skills:approve`, `skills:admin` | ✅ live (v0.16) | Approved instruction load, install-request lifecycle, org registries/packages/assignments |
| `skills_verify:run` | ✅ live (platform, tier-coupled) | The works-in harness protocol (claim / projection / result). Only a platform admin may mint or rotate a key with it, and the key works only while the user it runs as and the admin who minted or last rotated it are both still active platform admins |
| `skills_registry:poll` | ✅ live (platform, tier-coupled) | The registry poller's scheduler credential (`POST /api/v1/admin/skills/registries/poll`). Only a platform admin may mint or rotate a key with it, and the key works only while the user it runs as and the admin who minted or last rotated it are both still active platform admins |
| `platform_sweeps:run` | ✅ live (platform, tier-coupled) | The scheduled sweeps' credential: catalog regenerate, verify sweep, freshness sweep, rescan, publisher recheck, the GitHub webhook-delivery sweep, and (v0.23.0) the KB compile, org digest and helper retention sweeps. Only a platform admin may mint or rotate a key with it, and the key works only while the user it runs as and the admin who minted or last rotated it are both still active platform admins |
| `admin_metrics:read` | ✅ live (platform, tier-coupled, v0.23.0) | `GET /api/v1/admin/metrics` (Prometheus). Only a platform admin may mint or rotate a key with it, and the key works only while the user it runs as and the admin who minted or last rotated it are both still active platform admins |
| `sessions:read`, `rules:read`, `rules:write`, `retrieval_audit:read`, `admin:*` | Reserved | Not yet opted in on any route |

**Tier-coupled scopes.** The four `platform` scopes above are *tier-coupled*: they are mint/rotate-only by a platform admin **and** the key keeps working only while both the user it runs as and the admin who minted or last rotated it are still active platform admins. Demoting or deactivating either one stops the key with a `403` that names the minter's current tier and the fix (restore the minter, or mint a new key as a user who stays a platform admin). Minting and rotating a tier-coupled key returns a `warnings` array with a `minter_tier_coupling` entry so the operator knows before they build a job around it, and `service-keys list` exposes `coupling_ok` (`true`/`false`/`null`) plus `coupling_reason` so a silently-broken key is visible. Making someone a platform admin just long enough to mint a key doesn't work: the key stops as soon as they're demoted (v0.28.0 makes this visible; the rule itself is unchanged).

**Grant list pages and incompleteness.** The install-request list and both assignment lists are keyset-paginated: pass `limit` (1–500, default 100) and `cursor` (the previous page's `next_cursor`). Every response is `{"items": [...], "incomplete": bool, "omitted_count": int, "has_more": bool, "next_cursor": str|null, "generation": str}` (the install-request list also carries `can_approve`). Pages are in a stable id order; keep requesting with `cursor=next_cursor` until `has_more` is false - only then is the set complete. A page can hold fewer than `limit` items (filters and omitted records). An invalid `cursor` is a 422. `generation` is an opaque token for the collection's state, carried inside every cursor: if anything in the collection changes while you page (a grant created, decided, revoked or deleted, a membership change for the caller's assignment list, or a moderation action affecting one of its versions), the next page returns `409 listing_changed` - restart from the first page. The lists never guess a grant's targeting: a stored record whose `target_tools` or `requested_capabilities` is not a list of known names is omitted from its page, and that page reports `incomplete: true` with the count in `omitted_count`; treat the whole set as incomplete if any page was. Fetching or approving such a record directly returns `500 grant_record_corrupt`, and it never grants anything.
