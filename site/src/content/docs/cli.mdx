
## `sfs resume`

Resume a captured session in any supported AI tool.

```
sfs resume SESSION_ID [OPTIONS]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `SESSION_ID` | yes | Session ID or prefix |

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `--project` | path | — | Target project path (overrides workspace) |
| `--in` | string | `claude-code` | Target tool: `claude-code`, `codex`, `copilot`, or `gemini` |
| `--model`, `-m` | string | — | Model to use in target tool (e.g. `gpt-4.1`, `claude-sonnet-4`, `gemini-2.5-pro`) |
| `--no-rules-sync` | flag | `false` | Skip preflight of the target tool's project rules file. Per-invocation only. |
| `--force-rules` | flag | `false` | Overwrite an unmanaged target-tool rules file with SessionFS-managed content. One-time permission — the file becomes SessionFS-managed afterward and subsequent resumes refresh it normally. |

Converts the session to the target tool's native format and injects it into that tool's session storage. Cursor, Cline, Roo Code, Kilo Code, Antigravity, and Amp are capture-only — `--in cursor` (and the others) is rejected with an error. Use `--in` with one of the four supported resume targets instead.

Before launching the target tool, `sfs resume` preflights the tool's project rules file from the current canonical SessionFS rules. Missing files are written; SessionFS-managed files are refreshed; unmanaged files are left alone with a warning on stderr unless `--force-rules` is passed. Preflight failures are non-fatal — resume still exits `0`. See [Resume-Time Rules Sync](/docs/rules/#resume-time-rules-sync) for the full policy.

**`--model` support per tool:**
- **Claude Code**: passed as `--model` to the `claude` binary
- **Codex**: used in session injection and `codex resume --model`
- **Gemini**: passed as `--model` to the `gemini` binary
- **Copilot**: not supported (warns, uses Copilot's default)

If omitted, each tool uses its own default model.

**Examples:**

```bash
$ sfs resume ses_abc123 --in codex

Source session used rules v3 (sessionfs).
Current project rules are v5.
Synced codex.md from SessionFS rules v5.
Launching codex resume ...

Session resumed successfully.
  CC Session ID: abc123-def456
  JSONL: /Users/me/.claude/projects/.../abc123-def456.jsonl
  Messages: 23
```

Skip preflight for a one-off resume:

```bash
$ sfs resume ses_abc123 --in codex --no-rules-sync
```

Take ownership of a hand-written `codex.md`:

```bash
$ sfs resume ses_abc123 --in codex --force-rules
```

## `sfs daemon status`

Show daemon status and watcher health.

```
sfs daemon status
```

**Example:**

```bash
$ sfs daemon status

         SessionFS Daemon Status
┌──────────────────┬────────────────────────┐
│ Field            │ Value                  │
├──────────────────┼────────────────────────┤
│ PID              │ 12345                  │
│ Running          │ Yes                    │
│ Sessions         │ 47                     │
│ Watcher: cc      │ healthy (47 sessions)  │
└──────────────────┴────────────────────────┘
```

If pushes for a session keep failing (server errors, rate limits, network), the daemon backs off instead of retrying every cycle: after 1 minute, 5 minutes, 15 minutes, then hourly. After a long failing streak (12 attempts over at least six hours) it pauses that session until the session changes, the daemon restarts, or you run `sfs daemon retry-sync`. `sfs daemon status` lists these sessions with their failure count and last error, and `sfs doctor` reports them under "Sync retries".

## `sfs daemon retry-sync`

Retry sessions whose sync is backing off or paused after failed pushes, on the daemon's next sync cycle.

```
sfs daemon retry-sync [SESSION_ID]
```

| Argument / Option | Description |
|----------|-------------|
| `SESSION_ID` | Retry just this session (a unique prefix of its ID also works). Omit to retry every session that is backing off or paused. |
| `--config PATH` | The config file the daemon was started with, if you started it with `sfs daemon start --config`. |

**Example:**

```bash
$ sfs daemon retry-sync ses_abc12345
```

## `sfs config default-org`

Set or clear the server-canonical default organization used when capturing sessions and creating projects. Available starting v0.10.0.

```
sfs config default-org [ORG_ID | --clear]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `ORG_ID` | no | Org ID to use as default. Pass `--clear` to drop the preference. |

The value is persisted on the server (`users.default_org_id`) and returned in `GET /auth/me`. Membership is validated — non-members cannot set an org as default.

**Example:**

```bash
$ sfs config default-org acme_eng

Default organization set to acme_eng.
```

## `sfs audit`

```

```

| Argument | Required | Description |
|----------|----------|-------------|
| `SESSION_ID` | yes | Session ID or prefix |

| Option | Type | Default | Description |

| `--base-url` | string | — | Custom OpenAI-compatible endpoint (LiteLLM, vLLM, Ollama) |
| `--consensus` | flag | `false` | Run 3 passes, report where 2+ agree (3x cost) |
| `--report` | flag | `false` | Show existing report only |
| `--json` | flag | `false` | Output as JSON |
| `--format` | string | — | Export: `json`, `markdown`, `csv` |

```bash

HIGH      file_existence msg #12  "Created validator.py" -> No Write call
```

## `sfs delete`

Delete a session from the cloud, the local device, or both. Requires an explicit scope flag -- there is no default.

```
sfs delete SESSION_ID [OPTIONS]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `SESSION_ID` | yes | Session ID or prefix |

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `--cloud` | flag | -- | Delete from server, keep local copy |
| `--local` | flag | -- | Remove local copy, keep cloud copy |
| `--everywhere` | flag | -- | Delete from both server and local |
| `--force` | flag | `false` | Skip confirmation prompt |

If no scope flag is provided, the command prints an error and exits.

**Examples:**

```bash
# Remove from cloud only (local copy stays)
$ sfs delete ses_abc123 --cloud
Delete ses_abc123 from cloud? Local copy will be kept. [y/N] y
Deleted from cloud. Recoverable for 30 days.

# Remove from this device only
$ sfs delete ses_abc123 --local
Delete ses_abc123 from this device? Cloud copy is unaffected. [y/N] y
Removed local copy.

# Delete everywhere (recoverable for 30 days)
$ sfs delete ses_abc123 --everywhere --force
Deleted from cloud and local device. Recoverable for 30 days.
```

See [Delete Lifecycle](/docs/delete-lifecycle/) for full details on retention, recovery, and sync behavior.

## `sfs push`

Push a session to the cloud.

```
sfs push SESSION_ID [--yes] [--timeout SECONDS]
```

| Option | Description |
|--------|-------------|
| `--yes`, `-y` | Skip interactive confirmations (DLP findings, cloud-undelete). Findings are still shown. |
| `--timeout SECONDS` | How long to wait for the server to accept the upload (1–3600). Defaults to `SFS_UPLOAD_TIMEOUT`, then `upload_timeout` under `[sync]` in `config.toml`, then 300. Raise it for very large sessions on servers that run DLP scans. |

If the server doesn't answer in time, the push stops with a message saying so and how to raise the limit, instead of retrying the same upload.

## `sfs pull`

## `sfs sync`

Bidirectional sync and autosync management.

### `sfs sync` (default)

Run bidirectional sync — push local changes, pull remote-only sessions.

```
sfs sync
```

### `sfs sync auto`

Set autosync mode.

```
sfs sync auto --mode MODE
```

| Mode | Behavior |
|------|----------|
| `off` | No autosync (default). Manual `sfs push` only. |
| `all` | Every new or updated session auto-pushes to cloud. |
| `selective` | Only sessions in the watchlist auto-push. |

### `sfs sync watch`

Add sessions to the autosync watchlist (selective mode).

```
sfs sync watch SESSION_ID [SESSION_ID...]
```

### `sfs sync unwatch`

Remove sessions from the autosync watchlist.

```
sfs sync unwatch SESSION_ID [SESSION_ID...]
```

### `sfs sync watchlist`

Show all sessions in the autosync watchlist.

```
sfs sync watchlist
```

### `sfs sync status`

Show current autosync mode, counts, and storage usage.

```
sfs sync status
```

## `sfs project`

Manage shared project context — a single document shared across the team via MCP.

### `sfs project init`

Create a project context for the current repo (matched by git remote).

```
sfs project init [--org ORG_ID | --personal]
```

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `--org` | string | — | Create the project scoped to the given organization (caller must be a member) |
| `--personal` | flag | default | Create the project under the caller's personal scope |

When `--org` is supplied, the project inherits the org's knowledge base creation defaults at create time. If neither flag is supplied, the project is personal-scope (pre-v0.10.0 behavior).

### `sfs project show`

Display the current project context with metadata.

```
sfs project show
```

### `sfs project edit`

Open the context document in `$EDITOR`. Changes upload on save.

```
sfs project edit
```

### `sfs project set-context`

Set project context from a file.

```

```

### `sfs project get-context`

```
sfs project get-context

```


**Example:**

### `sfs project rebuild`

Force a full re-compile of the project context. Resets `compiled_at=NULL` on all active claims and clears `context_document`, so the next compile pass pulls every active claim from scratch. Useful on settled projects where normal `compile` would be a no-op.

```

```

**Example:**

```bash
$ sfs project rebuild

Project context reset. Run `sfs project compile` to regenerate.
```

### `sfs project transfer`

Initiate, accept, reject, or cancel a project transfer between scopes (personal &harr; org, or org &harr; org). Available starting v0.10.0.

**Example:**

## `sfs admin override`

Audited operator overrides (platform admin only).

```
sfs admin override project-transfer PROJECT_ID --to-org ORG_ID --reason "..." [--new-owner USER_ID] [--expect-from ORG_ID|personal] [--force] [--yes]
sfs admin override project-transfer --propose --project PROJECT_ID --org ORG_ID --reason "..."
sfs admin override record --action NAME --target-type TYPE --target-id ID --reason "..." [--before-file F] [--after-file F]
sfs admin override user-merge SOURCE_USER_ID TARGET_USER_ID --reason "..." [--apply] [--yes] [--json]
sfs admin override project-merge SOURCE_PROJECT_ID TARGET_PROJECT_ID --reason "..." [--persona-policy rename|skip|merge_content] [--apply] [--yes] [--json]
```

`project-transfer` moves a project into an organization without the owner's consent. It keeps the normal transfer checks (merged projects and stranded org personas are refused unless `--force`), cancels any pending transfer, and commits the move together with an audit entry holding the reason and before/after state. The owner must be a member of the destination organization; otherwise pass `--new-owner` with an active member, who becomes the owner. `--expect-from` refuses the move unless the project is still in the given org (or `personal`), so a retried command cannot move it twice. With `--propose` (v0.23.0) nothing is forced: the command asks the owner of a **personal** project to move it into an org, and the project moves only when the owner accepts (`POST /api/v1/orgs/{org_id}/projects/{project_id}/propose-transfer`). The caller must be an owner or admin of the destination org, and the project owner must be an active member of it. One pending transfer per project (`409 transfer_pending`); the same project and org can't be proposed again for 7 days after a decline or 24 hours after a cancel (`409 proposal_cooldown`); an org can hold at most 10 pending proposals (`409 proposal_limit`); proposals expire after 7 days. Use `--project` and `--org` in this mode. `record` logs an action performed outside the API, such as raw SQL; it is stored with source `operator_record`. Reasons are 1-500 characters; state files must hold a JSON object of at most 64 KiB.

### `sfs admin override user-merge`

Fold a duplicate account (for example a signup with a typo in the email) into the account to keep. Calls `POST /api/v1/admin/users/{source_id}/merge-into/{target_id}`. **Dry run by default**: it writes nothing and prints, per table, how many rows would be reassigned, deduplicated, revoked or cancelled (`--json` includes the row ids). `--apply` performs the merge in one transaction, deactivates the source user, revokes its API keys and writes exactly one `user_merge` audit entry with the reason and the state before and after. Prompts for confirmation when applying unless `--yes`.

- **Reassigned to the target:** sessions, projects, share links, bookmarks, handoffs, knowledge entries, context compilations, tickets (creator, resolver, comments, edits), wiki revisions, personas (creator and represented member), work queues, rules, GitHub installation and the source's plan records. Source storage usage is added to the target's. A session alias the target already uses is cleared, and the sync watchlist keeps one row per session.
- **Deduplicated:** org memberships (the higher role wins, the target on ties), and team memberships, devices, GitLab settings and judge settings (the target's row wins).
- **Revoked, never moved:** API keys (including service keys), trusted-reviewer bindings, SSO break-glass grants and SSO identities, and pending ownership or project transfers involving the source.
- **Left alone:** audit and history tables, so past actions keep the original actor.

The merge refuses, changing nothing, when source and target are the same (`400`); either user does not exist (`404`); the target is inactive (`409 target_inactive`); the source is a platform admin (`409 source_is_platform_admin`); the source has billing attached (`409 source_has_billing`); both users hold an active plan (`409 entitlement_conflict` — it never guesses which plan to keep); the source owns skill marketplace packages, publishers, listings or registries (`409 marketplace_assets_owned`); both have a GitHub installation (`409 github_installation_conflict`); or the source owns org projects in an org neither user belongs to (`409 project_owner_not_member`).

| Option | Default | Description |
|--------|---------|-------------|
| `--reason`, `-r` | required | Why the merge is needed (1-500 characters), stored in the audit log |
| `--apply` | off | Perform the merge. Without it the command is a dry run |
| `--yes`, `-y` | off | Skip the confirmation prompt when applying |
| `--json` | off | Print the raw JSON response, including the row ids |

### `sfs admin override project-merge`

Merge a duplicate project into the one to keep, whoever owns them. Use it when the owners can't run `sfs project merge` themselves, for example when the two projects belong to different users. Calls `POST /api/v1/admin/projects/{target_id}/merge-from/{source_id}`. It runs the same merge as `sfs project merge`: sessions, knowledge entries, wiki pages, tickets, personas, agent runs, handoffs and repos move to the target, and the source becomes a redirect to it. **Dry run by default**: prints the counts that would move. `--apply` merges in one transaction and writes one `project_merge` audit entry with the reason and the state before and after. Prompts for confirmation when applying unless `--yes`.

Both projects must be in the same org, or both personal (`400 cross_scope` otherwise: move one with `sfs admin override project-transfer` first). Owners don't have to match: merging one user's personal project into another user's gives the target's owner everything in the source, so check the dry run. It also refuses a project that is already merged or has a pending transfer.

| Option | Default | Description |
|--------|---------|-------------|
| `--reason`, `-r` | required | Why the merge is needed (1-500 characters), stored in the audit log |
| `--persona-policy` | `rename` | What to do when both projects have a persona with the same name: `rename`, `skip` or `merge_content` |
| `--apply` | off | Perform the merge. Without it the command is a dry run |
| `--yes`, `-y` | off | Skip the confirmation prompt when applying |
| `--json` | off | Print the raw JSON response |
